Concurrency Strategy

A race condition can occur when two administrators try to confirm two different, overlapping bookings for the same room at effectively the same instant. If each request were allowed to independently check for a conflicting confirmed booking and then commit, both checks could pass before either commits, resulting in two confirmed bookings for the same room and time slot — a double booking.

To prevent this, the booking confirmation process wraps the conflict check and the status update together in a single database transaction running at the highest available isolation level, Serializable. Under the default isolation level, two concurrent transactions could each read "no conflicting booking exists" before either one commits its change, and both would proceed. Serializable isolation closes that gap: it forces a second transaction touching the same room and time range to wait until the first transaction has fully committed or rolled back. By the time the waiting transaction's own conflict check actually runs, it sees the other administrator's already-committed change and correctly detects the conflict, refusing to confirm.

Two additional safeguards back this up. A row-versioning column that Entity Framework Core checks automatically on every update acts as a secondary safety net against similar races elsewhere in the codebase, causing a losing update to fail cleanly rather than silently overwrite another change. Separately, the increased chance of a database deadlock under this stricter isolation level is handled explicitly: a deadlock is recognized and translated into a proper conflict response for the caller, rather than being allowed to surface as an unhandled server error.

The end result is that exactly one of the two competing confirmation requests succeeds, and the other receives a clean conflict response instead of succeeding or crashing. This was verified directly, not just assumed: by deliberately holding open a conflicting database transaction and confirming that a competing confirmation request correctly blocks, then fails cleanly once the lock is released, with no duplicate or partially-applied data left behind afterward.
